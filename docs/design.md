## Таблица логов

```
timestamp    DateTime64(3, 'UTC') CODEC(Delta, ZSTD(1))
user_id      UInt64
search_query LowCardinality(String)
query_norm   LowCardinality(String) MATERIALIZED …
ENGINE MergeTree PARTITION BY toDate(timestamp) ORDER BY (user_id, timestamp)
```

Замер: сжатый размер колонок на копиях таблицы после `OPTIMIZE FINAL`. Копии созданы с `min_bytes_for_wide_part = 0`, иначе ClickHouse не считает размер по колонкам. Сама `search_log` на таком объёме хранится в compact-частях (по одной на день) и занимает 11,37 МиБ вместе с `query_norm`; сравнение вариантов между собой от этого не меняется.

| Вариант | timestamp | search_query | user_id | итого без query_norm |
|---|---|---|---|---|
| выбранный | 3,20 МиБ | 2,05 МиБ | 1,65 МиБ | 6,90 МиБ |
| без кодека `Delta` | 4,92 МиБ | | | 8,62 МиБ |
| `String` вместо `LowCardinality` | | 4,80 МиБ | | 9,66 МиБ |
| `ORDER BY (timestamp, user_id)` | 0,49 МиБ | 2,22 МиБ | 4,13 МиБ | 6,84 МиБ |

Сортировка по времени весит почти столько же, поэтому ключ выбран по форме запроса: окно `PARTITION BY user_id ORDER BY timestamp` читает данные в том порядке, в котором они лежат на диске.

`query_norm` стоит ещё 1,77 МиБ. Взамен регулярное выражение не прогоняется на каждой пересборке и в каждом отчёте, а исходный текст остаётся для разбора. Колонка использует то же выражение, что функция `normalize_search`, а совпадение проверяет `004_checks.sql`.

Партиции по дням: 7 частей на неделю данных. Это удобно для пересчёта по дням и для TTL. На годе логов будет около 365 партиций, это нормально для ClickHouse.

## Таблица тегов

`query String, tag String, users UInt32, rank UInt8`, `ORDER BY (query, rank)`: поиск по точному `query` идёт по первичному ключу и читает одну-две гранулы, а строки уже идут по `rank`. Порядок задаётся сортировкой `users DESC, tag`. `rank` считается после `LIMIT 10 BY query`, поэтому не может выйти за UInt8 даже у запроса с сотнями кандидатов (тест на 300 кандидатов есть).

Сборка идёт в `query_tags_next` (`003_tags.sql`), затем `004_checks.sql` проверяет именно её, и только после этого `005_publish.sql` делает `EXCHANGE TABLES`. Если проверка не прошла, загрузчик останавливается, а сервис продолжает отдавать прежние теги: это проверено тестом, который ломает сборку восемью способами. Логи загружаются через такую же подмену, поэтому повторный `docker compose up` их не задваивает.

## Сервис

- `database/sql` + `clickhouse-go`, значение подставляется через `?`. Кавычки, `\`, `?`, `{…}` и битые байты проверены интеграционным тестом.
- Нормализация в Go повторяет `lowerUTF8` из ClickHouse 24.8, а не `strings.ToLower`: у ClickHouse более старая таблица регистров (600 символов вроде `İ`, знака кельвина, грузинского мтаврули он не меняет), а некорректные байты он оставляет как есть. Тест сверяет обе реализации на всех кодовых точках Unicode, поэтому при обновлении образа расхождение сразу будет видно.
- Таймаут `REQUEST_TIMEOUT` действует и на запрос, и на установку соединения: контекст на dial в драйвере не влияет. При зависшей базе ответ приходит за 2 с со статусом 504, а `/healthz` отдаёт 503.
- Если клиент ушёл, ответ не пишем и ошибкой это не считаем. Текст поискового запроса в логи не попадает.
- Шаблон вшит в бинарник через `embed`, а образ собран `FROM scratch` (23 МБ).
