# Ежедневный пересчёт

Сейчас теги пересчитываются по всем логам целиком. На неделе данных это занимает секунды, но время растёт вместе с историей. Ежедневно я бы пересчитывал только новый день и складывал результат с уже посчитанным.

## Что хранить

Промежуточная таблица с парами за каждый день:

```sql
CREATE TABLE pair_users_daily
(
    day   Date,
    query String,
    tag   String,
    users AggregateFunction(uniqExact, UInt64)
)
ENGINE = AggregatingMergeTree
PARTITION BY day
ORDER BY (query, tag, day);
```

Хранится состояние `uniqExact`, а не готовое число. Человек, который делал одну и ту же пару в понедельник и во вторник, должен посчитаться один раз. Сумма дневных чисел посчитала бы его дважды, а слияние состояний — нет.

## Что делать каждую ночь

1. Загрузить логи за день D в партицию `search_log`: `REPLACE PARTITION` из временной таблицы, чтобы повторный запуск не задваивал данные.
2. Посчитать пары, у которых **второй** запрос сделан в день D. Для этого прочитать логи с `D 00:00 − 30 минут`, потому что первый запрос пары мог быть сделан вчера в 23:50. Пары, у которых второй запрос во вчерашнем хвосте, отбросить: они уже учтены вчера.
3. Записать результат в отдельную таблицу и заменить им партицию D в `pair_users_daily` (`REPLACE PARTITION`). Пересчёт того же дня безопасен.
4. Собрать `query_tags_next`: `uniqExactMerge(users)` по нужному окну (например, за последние 30 дней), затем `HAVING users >= 5`, `LIMIT 10 BY query`, и подменить через `EXCHANGE TABLES`, как сейчас.

## Опоздавшие события

Если события дня D приходят позже, пересчитываются партиции D и D+1: от последнего события дня D зависит первая пара дня D+1. Остальные дни не меняются.

## Что ещё

- TTL на `search_log` и `pair_users_daily` по окну, за которое строятся теги, чтобы история не росла бесконечно.
- `uniqExact` хранит множества пользователей. Если по памяти станет тяжело, можно перейти на `uniqCombined`. На малых множествах он точный (сначала массив, потом хеш-таблица, HLL только на больших), поэтому порог в 5 человек не сдвинется. Погрешность около 1% появится только у популярных пар: могут немного поменяться числа и порядок близких по `users` тегов.
- Запускать по расписанию (cron, Airflow) скриптом из тех же SQL-файлов. Порядок тот же, что сейчас в `db/load.sh`: сборка в `query_tags_next`, `004_checks.sql` по ней и `EXCHANGE` только при пройденных проверках.
