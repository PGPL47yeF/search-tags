# search-tags

Поисковые теги: для запроса показываем до 10 запросов, которые люди ищут сразу после него.
Пара считается, если второй запрос идёт следующим у того же пользователя не позже чем через 30 минут и отличается от первого. Тег попадает в выдачу, если пару сделали не меньше 5 разных пользователей.

## Запуск

```sh
cp /путь/к/logs.parquet data/logs.parquet
docker compose up --build
```

`loader` создаёт таблицы, загружает логи, собирает теги в отдельную таблицу, проверяет их (`db/004_checks.sql`) и только потом публикует. Если проверка не прошла, теги не публикуются, а сервис не стартует (или, при повторном запуске, продолжает отдавать прежние). Дальше:

- страница: http://localhost:8080/?q=платье
- API: `GET /api/tags?q=платье` → `[{"tag":"красное платье","users":9264}, …]`; пустой `q` → 400, тегов нет → `[]`
- `GET /healthz`

Настройки сервиса берутся из env: `HTTP_PORT`, `REQUEST_TIMEOUT` (2s), `CLICKHOUSE_ADDR`, `CLICKHOUSE_DB`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`. Порты на хосте: `APP_PORT` (8080) и `CLICKHOUSE_PORT` (9000, нужен только для интеграционных тестов) — поменяйте, если заняты.

Тесты: `go test ./...`. Интеграционные — на поднятом `docker compose` (без `CLICKHOUSE_ADDR` они пропускаются, с ним — падают при любой ошибке подключения):

```sh
CLICKHOUSE_ADDR=localhost:9000 CLICKHOUSE_USER=tags CLICKHOUSE_PASSWORD=tags go test -tags integration ./test/integration
```

Результаты последнего прогона лежат в [`results/`](results).

## Почему так

- **`search_log`**: `MergeTree`, `ORDER BY (user_id, timestamp)`. Главный запрос идёт окном по пользователю в порядке времени, и данные уже лежат в этом порядке. Партиции по дням, чтобы пересчитывать и удалять по одному дню.
- Нормализованный запрос хранится в `MATERIALIZED`-колонке рядом с исходным: считается один раз при вставке, исходник остаётся для разбора.
- `DateTime64(3, 'UTC')`: такой тип у колонки в parquet. Сейчас все метки — целые секунды, но точность не теряем, и граница 30:00.000 сравнивается точно. `LowCardinality(String)`: 11 тыс. написаний на миллион строк. `Delta` по времени: −35% на колонке.
- **`query_tags`**: `ORDER BY (query, rank)`, сервис читает по точному `query` уже в нужном порядке. Собирается в соседнюю таблицу, проверяется и только потом подменяется через `EXCHANGE`: API видит либо старые проверенные теги, либо новые.

Подробнее с замерами: [docs/design.md](docs/design.md).

## Допущения

- Пустые после нормализации запросы выбрасываются до поиска соседей и не разрывают пару.
- Пробелом считается `\s` (пробел, таб, переводы строк), неразрывный пробел остаётся частью запроса. Go и SQL нормализуют одинаково: регистр переводится по правилам `lowerUTF8` из ClickHouse (у него своя таблица регистров, а битые байты он не трогает), и интеграционный тест сверяет обе реализации на всех 1 112 064 символах Unicode и всех 11 018 написаниях из логов.
- При равном числе пользователей теги идут по алфавиту. При одинаковом времени у одного пользователя порядок задаёт текст запроса; в этих логах таких случаев нет.
- Грязь в данных (регистр и пробелы в 9% строк, два бота) описана в [docs/design.md](docs/design.md#что-в-данных).

Ежедневный пересчёт (бонус): [docs/daily-refresh.md](docs/daily-refresh.md).
