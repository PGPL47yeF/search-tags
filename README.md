# search-tags

Поисковые теги: для запроса показываем до 10 запросов, которые люди ищут сразу после него.
Пара считается, если второй запрос идёт следующим у того же пользователя не позже чем через 30 минут и отличается от первого. Тег попадает в выдачу, если пару сделали не меньше 5 разных пользователей.

## Запуск

```sh
cp /путь/к/logs.parquet data/logs.parquet
docker compose up --build
```

`loader` создаёт таблицы, загружает логи, собирает теги и прогоняет проверки (`db/004_checks.sql`): если хоть одна не прошла, сервис не стартует. Дальше:

- страница: http://localhost:8080/?q=платье
- API: `GET /api/tags?q=платье` → `[{"tag":"красное платье","users":9264}, …]`; пустой `q` → 400, тегов нет → `[]`
- `GET /healthz`

Настройки сервиса берутся из env: `HTTP_PORT`, `REQUEST_TIMEOUT` (2s), `CLICKHOUSE_ADDR`, `CLICKHOUSE_DB`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`. Внешний порт меняется через `APP_PORT`.

Тесты: `go test ./...`, с ClickHouse — `go test -tags integration ./test/integration` (переменные те же). Результаты последнего прогона лежат в [`results/`](results).

## Почему так

- **`search_log`**: `MergeTree`, `ORDER BY (user_id, timestamp)`. Главный запрос идёт окном по пользователю в порядке времени, и данные уже лежат в этом порядке. Партиции по дням, чтобы пересчитывать и удалять по одному дню.
- Нормализованный запрос хранится в `MATERIALIZED`-колонке рядом с исходным: считается один раз при вставке, исходник остаётся для разбора.
- `DateTime64(3, 'UTC')`: в логах миллисекунды, а граница 30 минут включительная. `LowCardinality(String)`: 11 тыс. написаний на миллион строк. `Delta` по времени: −35% на колонке.
- **`query_tags`**: `ORDER BY (query, rank)`, сервис читает по точному `query` уже в нужном порядке. Пересобирается в соседнюю таблицу и подменяется через `EXCHANGE`, поэтому API не видит пустую таблицу.

Подробнее с замерами: [docs/design.md](docs/design.md).

## Допущения

- Пустые после нормализации запросы выбрасываются до поиска соседей и не разрывают пару.
- Пробелом считается `\s` (пробел, таб, переводы строк), неразрывный пробел остаётся частью запроса. Go и SQL нормализуют одинаково: интеграционный тест сверяет все 11 018 написаний из логов.
- При равном числе пользователей теги идут по алфавиту. При одинаковом времени у одного пользователя порядок задаёт текст запроса; в этих логах таких случаев нет.
- Грязь в данных (регистр и пробелы в 9% строк, два бота) описана в [docs/design.md](docs/design.md#что-в-данных).
